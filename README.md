# 🍜 每日饮食推荐系统

一个**加权打分 + 时间衰减**的推荐引擎，用来解决"今天吃什么"这个日常决策问题。

零依赖实现：只用 JDK 自带的 HTTP Server，不需要 Spring、不需要数据库、不需要联网。

## 为什么做这个

"今天吃什么"看起来是个随便选选的问题，但它和一个真实的推荐系统面对的是同一组核心矛盾：

- **利用 vs 探索**：总推你爱吃的，你会腻；总推新菜，你可能不满意
- **时间维度**：刚吃过的菜不该再推，但隔久了要好回来
- **候选集退化**：过滤条件一多，可选集合可能直接空掉

所以我把它当成一个**缩小版的推荐系统**来做：设计打分模型 → 实现 → 做对比实验验证每一部分的贡献。

## 核心算法

```
score(dish) = α · 偏好分 P + β · 时间分 R + γ · 场景分 C − 惩罚分 + 探索噪声
```

### 时间分：这是一切的核心

```
R = 1 − exp(−Δt / λ)
```

| 距上次吃 Δt（天） | R（λ=3） | 直观含义 |
|---|---|---|
| 0 | 0.00 | 刚吃过，完全排除 |
| 1 | 0.28 | 还很饱 |
| 3 | 0.63 | 开始想吃了 |
| 7 | 0.90 | 强烈想吃 |
| 14 | 0.99 | 逼近上限 |

**两个关键设计决策**

1. **上限为 1，不能无限增长。** 如果用线性递增，一道放了一年的菜会永远霸榜，推荐结果就退化了。指数回升天然收敛。
2. **λ 按菜系个性化。** 清淡的（健康餐 / 汤羹 / 家常）λ × 1.6，可以天天吃；重口的（火锅 / 川菜 / 湘菜）λ × 0.7，容易腻。

> 这个函数和间隔重复记忆（Anki）的遗忘曲线、推荐系统的时效衰减是同一个数学模型。

### 偏好分

```
P = 基础评分(0~5 星归一化) + 常吃加成(≤0.10) + 反馈修正(±0.20)
```

没打过分的菜给 **0.60** 的中性值，避免新菜被永久埋没（冷启动处理）。

### 场景分

- 雨 / 冷 → 汤、暖胃、炖菜 **+0.30**，清爽低卡 −0.10
- 热 → 清爽、凉菜 **+0.30**，炖菜、重辣 −0.10

### 惩罚分与候选池自适应

- 7 天内吃过 → 按天数线性降权
- 3 天内吃辣 / 油腻超过 2 次 → 对应菜品降权
- **惩罚项乘以 β**：它属于时间维度，做消融实验（β=0）时必须一起归零，否则对照组不干净

**候选池自适应**：硬性排除最近 N 天吃过的菜，会导致候选集为空。系统会逐天放宽窗口（3 天 → 2 天 → 1 天 → 0 天），保证永远有菜可选：

```
配置排除 3 天 → 候选不够 → 试 2 天 → 还不够 → 试 1 天 → 试 0 天 → 一定出结果
```

对应工业界的常见做法：**过滤条件导致候选集为空时降级，而不是报错。**

## 实验验证

### 实验一：时间衰减闭环

固定一道菜（宫保鸡丁，5 星），只改变"距上次吃"的天数：

| 距上次吃 | 时间分 R | 结果 |
|---|---|---|
| 0 天 | — | 被硬性排除 |
| 2 天 | — | 被硬性排除 |
| 5 天 | 0.908 | 排名第 1 |
| 10 天 | 0.992 | 排名第 1 |

R 值与公式 `1 − exp(−Δt/3)` 完全吻合：`1 − e^(−5/3) = 0.908`，`1 − e^(−10/3) = 0.992`。

### 实验二：消融实验（验证时间衰减的真实贡献）

同一组数据，只改 β：

| 设置 | 宫保鸡丁（8 天没吃） | 扬州炒饭（4 天没吃） |
|---|---|---|
| β = 0.30（启用） | **0.943** | **0.852** ← 时间衰减拉开差距 |
| β = 0.00（对照组） | 0.650 | 0.650 ← 完全持平 |

**这说明时间衰减项确实在起作用，而不是被其他因素掩盖。**

### 实验三：候选池耗尽

把 26 道午餐类菜品**全部**标记为"今天吃过"：

| | 候选数 | 实际排除天数 | 结果 |
|---|---|---|---|
| 吃之前 | 15 道 | 3 天 | 正常推荐 |
| 全吃遍后 | 15 道 | **0 天**（自动放宽） | 仍能推荐，按喜好排序 |

系统没有返回空列表，而是自动降级 —— 这正是一个健壮的推荐系统该有的行为。

## 运行

**双击 `run.bat`** 即可（自动编译 + 启动 + 打开浏览器）。

或者手动：

```bash
javac -encoding UTF-8 -d out src/SparkServer.java
java -cp out foodrec.SparkServer 8080
```

访问 http://localhost:8080

**要求**：JDK 17+（开发环境 JDK 23）

---

## 界面功能

| 标签页 | 功能 |
|---|---|
| **今天吃什么** | 主推荐卡片 + 完整排名前 15，展示每道菜的**打分明细**（偏好 / 时间分 / 场景 / 惩罚） |
| **菜品库 · 打分** | 82 道菜，点星评分，按菜系 / 状态筛选搜索 |
| **吃过什么** | 历史记录 |
| **算法参数** | 拖滑块实时调 α / β / γ / λ / 噪声 / 排除天数 / 候选池保底 |

「换一换」每次重新打分，排名会有小幅波动 —— 这是探索噪声在起作用。

## API

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/recommend?meal=午餐&weather=雨&topN=6` | 获取推荐（含打分明细与候选池状态） |
| POST | `/api/eat?date=2026-10-05` | 记录吃过，body: `{"dish":"宫保鸡丁","rating":5}` |
| POST | `/api/rate` | 打分，body: `{"dish":"宫保鸡丁","stars":5}` |
| POST | `/api/feedback` | 反馈，body: `{"dish":"宫保鸡丁","good":true}` |
| GET/POST | `/api/params` | 读取 / 修改算法参数 |
| GET | `/api/stats` | 统计数据 |
| GET | `/api/dishes` | 菜品列表 |
| POST | `/api/reset` | 清空数据 |

**调试技巧**：`/api/eat?date=2026-10-01` 可以回填历史记录，用来观察时间衰减效果。

## 项目结构

```
food-recommender/
├── src/SparkServer.java   后端 + 推荐引擎 + 菜品库（单文件，约 850 行）
├── web/index.html         前端页面（原生 JS，无框架）
├── data/                  吃饭记录（本地生成，已加入 .gitignore）
│   ├── stats.tsv          每道菜的评分 / 次数 / 上次吃的时间
│   ├── history.txt        历史记录
│   └── params.tsv         算法参数
├── run.bat                一键编译 + 启动
└── build.bat              只编译
```

**关键代码位置**

| 想看什么 | 位置 |
|---|---|
| 打分公式 | `Recommender.score()` |
| 时间衰减 + 菜系个性化 λ | `Recommender.score()` / `lambdaFor()` |
| 候选池自适应 | `Recommender.recommend()` |
| 场景调整 | `Recommender.sceneAdjust()` |
| 数据持久化 | `DataStore.save()` / `load()` |

## 已知限制

- **单用户**：没有用户体系，数据存在本地文件。协同过滤需要多用户行为数据，当前规模下用基于内容的推荐是更合理的选择。
- **数据量小**：82 道菜、几十条记录，离真实推荐场景的规模差很远。
- **无离线评估**：目前的结论来自人工构造的实验，还没有系统的离线指标与真实流量验证。
